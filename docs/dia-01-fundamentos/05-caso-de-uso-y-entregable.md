# Caso de uso y entregable

Un caso de uso conecta una necesidad concreta con una tarea que puede realizarse mediante un modelo de lenguaje.

El entregable convierte ese trabajo en un resultado que otra persona puede revisar, comprender y utilizar.

Esta unidad cierra la primera jornada del curso de Prompt Engineering.

Su propósito es ayudarte a seleccionar una aplicación viable y a definir qué presentarás como evidencia de tu aprendizaje.

No necesitas resolver todavía un proyecto completo.

Necesitas establecer un punto de partida claro, un alcance razonable y una forma de comprobar los resultados.

Durante la sesión prepararás una ficha breve que servirá como referencia para las siguientes jornadas.

La ficha distinguirá la necesidad, los datos disponibles, el resultado esperado, los criterios de aceptación y las limitaciones.

**Un buen caso de uso no es el más ambicioso: es el que tiene un propósito reconocible y puede evaluarse con los recursos disponibles.**

## 1. Comprender el caso de uso

Antes de redactar un prompt, debemos comprender qué trabajo queremos mejorar y qué resultado necesita la persona destinataria.

Esta sección establece las distinciones necesarias para seleccionar una tarea útil y evitar proyectos demasiado amplios.

### 1.1. Ficha de la unidad

La unidad integra lo trabajado durante el primer día.

| Elemento | Descripción |
|---|---|
| Jornada | 1 · Fundamentos |
| Unidad | Caso de uso y entregable |
| Duración | 0,5 horas |
| Modalidad | Explicación, demostración y práctica |
| Resultado | Ficha inicial de caso de uso |
| Evaluación | Formativa |

No se requiere programación.

Una interfaz conversacional es suficiente para los ejemplos.

La ejecución de un prompt durante esta media hora es opcional.

La prioridad es definir y documentar.

**Esta unidad no exige una solución preparada para producción.**

### 1.2. Objetivos de aprendizaje

Al finalizar podrás describir una aplicación concreta de Prompt Engineering.

También podrás delimitar qué evidencia entregarás.

Los objetivos son:

- Identificar una necesidad.
- Convertirla en una tarea observable.
- Reconocer quién utilizará la respuesta.
- Definir los datos de entrada.
- Especificar el resultado esperado.
- Establecer criterios de aceptación.
- Documentar restricciones y riesgos.
- Proponer una primera prueba.

Estos objetivos se aplican a distintos perfiles profesionales.

No dependen de una plataforma específica.

**El resultado debe poder explicarse sin utilizar expresiones vagas.**

### 1.3. Qué es un caso de uso

Un caso de uso describe una situación en la que una persona o un sistema necesita realizar un trabajo.

En este curso lo utilizaremos para conectar:

- Una necesidad.
- Una persona destinataria.
- Una tarea.
- Una entrada.
- Una salida.
- Una comprobación.

No equivale simplemente a nombrar una tecnología.

“Utilizar IA en operaciones” es una intención general.

“Preparar una ficha de solicitudes a partir de correos” es una tarea delimitada.

La diferencia permite diseñar un prompt y evaluar su respuesta.

**El caso de uso debe describir trabajo, no solo una herramienta.**

### 1.4. Necesidad, tarea y solución

Estos tres conceptos están relacionados, pero no son equivalentes.

La necesidad explica qué problema existe.

La tarea describe qué actividad queremos realizar.

La solución propone cómo realizarla.

| Concepto | Pregunta principal |
|---|---|
| Necesidad | ¿Qué dificultad queremos reducir? |
| Tarea | ¿Qué trabajo debe completarse? |
| Solución | ¿Qué procedimiento utilizaremos? |

No debemos decidir la solución antes de comprender la necesidad.

Un modelo de lenguaje puede ser útil para parte del proceso.

Otra parte puede resolverse mejor con una plantilla o una regla.

**Seleccionar IA no es una obligación del diseño.**

### 1.5. Caso de uso, prompt y flujo de trabajo

El caso de uso establece el propósito.

El prompt concreta una instrucción dentro de ese propósito.

El flujo de trabajo incluye las actividades necesarias antes y después de generar la respuesta.

Un flujo sencillo puede contener:

1. Recibir un documento.
2. Revisar que pueda compartirse.
3. Ejecutar un prompt.
4. Comprobar la salida.
5. Corregir incidencias.
6. Preparar el resultado final.

El prompt no representa todo el proceso.

Tampoco sustituye automáticamente la revisión.

**Diseñar el caso de uso exige mirar más allá de la conversación.**

### 1.6. Quién utiliza el resultado

La persona usuaria del modelo y la destinataria de la salida pueden ser distintas.

Quien ejecuta el prompt puede preparar material para otra persona.

Eso afecta al lenguaje y al formato.

Identifica:

- Quién introduce los datos.
- Quién revisa la respuesta.
- Quién utiliza el entregable.
- Quién autoriza una acción posterior.

No es necesario asignar nombres reales.

Puedes utilizar funciones profesionales.

La responsabilidad debe quedar clara.

**Una salida sin destinatario definido es difícil de evaluar por utilidad.**

### 1.7. Qué decisión o actividad facilita

Una respuesta debe servir para algo reconocible.

Puede apoyar una decisión.

También puede facilitar una actividad sin decidir nada.

Por ejemplo:

- Preparar una reunión.
- Revisar una solicitud.
- Ordenar información.
- Crear un borrador.
- Detectar datos pendientes.
- Comparar alternativas.

No todos los casos necesitan automatizar una decisión.

En esta jornada priorizamos tareas de apoyo revisables.

La acción posterior debe quedar fuera del alcance si no está autorizada.

**Apoyar una decisión no equivale a tomarla.**

### 1.8. El proceso actual

Describe cómo se realiza la tarea sin el modelo.

Esta descripción establece una referencia inicial.

Puedes registrar:

- Qué información se recibe.
- Quién la revisa.
- Qué resultado se prepara.
- Qué dificultades aparecen.
- Qué errores son frecuentes.
- Qué comprobaciones ya existen.

No inventes mediciones de tiempo.

Si no has medido una duración, escribe que es una estimación.

Una práctica del curso tampoco demuestra ahorro real.

**La mejora necesita compararse con un proceso conocido.**

### 1.9. Valor esperado y valor demostrado

El valor esperado es una hipótesis.

El valor demostrado requiere evidencia.

Podemos esperar que una tarea resulte más rápida.

También podemos esperar una estructura más uniforme.

Eso no permite afirmar que la mejora ya se ha producido.

Distingue expresamente:

- Lo que quieres conseguir.
- Lo que has observado.
- Lo que todavía no has comprobado.

Una primera prueba puede mostrar viabilidad.

No necesariamente demuestra eficiencia sostenida.

**No presentes expectativas como resultados medidos.**

### 1.10. Tareas adecuadas para comenzar

Conviene seleccionar tareas pequeñas y verificables.

Las más accesibles suelen trabajar con información explícita.

Algunas opciones son:

- Resumir un documento breve.
- Extraer campos de un correo.
- Clasificar solicitudes con reglas.
- Reescribir un texto.
- Organizar notas.
- Generar un borrador.
- Detectar datos ausentes.

Cada opción necesita criterios propios.

No todas requieren conocimiento externo.

**Cuanto más clara sea la fuente, más sencilla será la primera comprobación.**

### 1.11. Tareas que conviene posponer

Algunas propuestas requieren más controles de los disponibles en esta sesión.

Conviene posponer:

- Decisiones médicas individualizadas.
- Resoluciones jurídicas.
- Evaluaciones de personas.
- Operaciones financieras.
- Acciones automáticas sobre sistemas.
- Procesos con datos sensibles.
- Automatizaciones sin supervisión.

Posponer no significa que toda aplicación futura sea imposible.

Significa que el caso necesita un diseño y una evaluación más amplios.

En el curso podemos trabajar con versiones sintéticas y limitadas.

**La viabilidad técnica no elimina la necesidad de gobernanza.**

### 1.12. El alcance mínimo viable

El alcance mínimo define la versión más pequeña que produce un resultado útil.

Debe conservar el propósito principal.

No debe convertirse en una demostración sin relación con la necesidad.

Compara estas propuestas:

```text
Propuesta amplia:
Automatizar toda la gestión de solicitudes de formación.

Alcance inicial:
Extraer requisitos explícitos de un correo ficticio.
Preparar una ficha interna revisable.
No responder ni aprobar la solicitud.
```

La segunda propuesta puede probarse durante el curso.

**Reducir alcance facilita aprender sin perder dirección.**

### 1.13. Qué queda fuera

Definir exclusiones evita expectativas equivocadas.

Una ficha puede incluir un apartado específico.

Ejemplo:

```text
Fuera del alcance:
- Enviar respuestas.
- Confirmar disponibilidad.
- Calcular precios.
- Consultar datos personales.
- Aprobar solicitudes.
```

Las exclusiones deben corresponder al flujo real.

No son una lista decorativa.

También ayudan a revisar si la respuesta excede la tarea.

**El alcance incluye lo que se hará y lo que no se hará.**

### 1.14. Viabilidad inicial

Una propuesta viable puede probarse con los medios disponibles.

Comprueba estas condiciones.

| Condición | Pregunta |
|---|---|
| Datos | ¿Disponemos de una entrada utilizable? |
| Herramientas | ¿Podemos realizar la tarea en el entorno autorizado? |
| Tiempo | ¿Cabe una primera prueba durante el curso? |
| Evaluación | ¿Sabemos reconocer un resultado correcto? |
| Seguridad | ¿Podemos practicar sin datos sensibles? |

Una respuesta negativa no exige descartar toda la idea.

Puede requerir reducir el alcance.

También puede requerir preparar datos sintéticos.

**La viabilidad debe revisarse antes de construir prompts extensos.**

### 1.15. Decisión de continuar, reformular o descartar

Al terminar la selección, toma una decisión explícita.

Puedes continuar si la propuesta es clara y verificable.

Puedes reformular si existe valor, pero el alcance es excesivo.

Puedes descartarla si no hay datos o criterios suficientes.

Registra:

```text
Decisión:
Motivo:

Qué mantengo:
Qué reduzco:
Qué necesito resolver:
```

Descartar una propuesta inadecuada no es un fracaso.

Es una decisión de diseño.

**Elegir bien el trabajo evita invertir esfuerzo en una solución difícil de justificar.**

## 2. Diseñar el entregable y la evidencia

Una vez seleccionado el caso, debemos definir qué se producirá y cómo se comprobará.

El entregable debe permitir que otra persona comprenda el trabajo sin reconstruir toda la conversación.

### 2.1. Dos tipos de entregable

En esta unidad distinguimos un resultado funcional y una evidencia académica.

El resultado funcional sirve a la tarea.

La evidencia académica documenta el aprendizaje.

| Tipo | Contenido |
|---|---|
| Resultado funcional | Ficha, resumen, tabla o borrador |
| Evidencia académica | Caso definido, prompt, pruebas y revisión |

Durante la media hora entregas principalmente la ficha de definición.

En las siguientes jornadas completarás pruebas y versiones.

No necesitas presentar ahora toda la evidencia final.

La distinción evita confundir una salida bonita con un trabajo documentado.

**El producto y su evaluación son partes diferentes del entregable.**

### 2.2. Características de un entregable útil

Un entregable debe tener un propósito y un destinatario.

También debe ser comprensible y revisable.

Características recomendadas:

- Identificación de la tarea.
- Estructura coherente.
- Información pertinente.
- Tratamiento de datos ausentes.
- Separación de hechos y propuestas.
- Limitaciones visibles.
- Evidencias accesibles.

No necesita incluir todas las respuestas completas en su cuerpo principal.

Puede utilizar anexos.

Los anexos deben poder localizarse.

**La documentación debe facilitar la revisión, no dificultarla.**

### 2.3. Definir la entrada

Describe qué material recibirá el prompt.

No basta con escribir “datos”.

Especifica:

- Tipo de documento.
- Contenido esperado.
- Extensión aproximada.
- Idioma.
- Estructura.
- Procedencia autorizada.
- Condiciones de privacidad.

La extensión puede ser orientativa si todavía no tienes muestras.

No inventes límites de la plataforma.

Comprueba las capacidades del entorno cuando sean relevantes.

**La entrada debe corresponder a lo que realmente podrás proporcionar.**

### 2.4. Preparar datos sintéticos

Los datos sintéticos se crean para practicar sin utilizar información real sensible.

Deben representar dificultades pertinentes de la tarea.

Pueden incluir:

- Campos completos.
- Campos ausentes.
- Fechas tentativas.
- Valores contradictorios.
- Expresiones ambiguas.
- Contenido irrelevante.

No necesitan reproducir todos los detalles de una organización.

Sí necesitan permitir una comprobación.

Identifica claramente que son ficticios.

**Los datos sintéticos reducen exposición, pero no demuestran rendimiento sobre datos reales.**

### 2.5. Definir la salida funcional

Describe qué debe recibir la persona destinataria.

Utiliza nombres de secciones o campos.

Ejemplo:

```text
Salida:
Una tabla con requisito, valor y estado.
Después, una lista de hasta tres preguntas de aclaración.
```

Evita expresiones como “un análisis completo” sin precisar contenido.

La salida debe ser compatible con el uso posterior.

Si será procesada automáticamente, define tipos de datos.

Si será leída por una persona, prioriza claridad.

**El formato se elige por utilidad, no por apariencia técnica.**

### 2.6. Campos obligatorios y opcionales

No todos los campos tienen la misma importancia.

Distinguirlos facilita comprobar completitud.

Un campo obligatorio debe aparecer aunque su valor sea desconocido.

Un campo opcional puede omitirse según una regla.

Ejemplo:

```text
Obligatorios:
Tema, participantes, duración y estado de la fecha.

Opcionales:
Observaciones adicionales presentes en la fuente.
```

Un campo obligatorio no exige inventar un valor.

Puede contener “No indicado”.

**La obligatoriedad se refiere a la estructura, no a la existencia del dato.**

### 2.7. Tratamiento de información ausente

Define una representación uniforme.

La elección depende del formato.

Para lectura humana puedes utilizar:

- No indicado.
- Pendiente de confirmar.
- No disponible.

Para datos estructurados puede utilizarse `null`.

No mezcles estos estados sin explicar su significado.

“No indicado” describe ausencia en la fuente.

“Pendiente” puede describir una condición explícita.

Una cifra cero representa un valor, no una ausencia.

**La falta de información debe permanecer visible.**

### 2.8. Tratamiento de contradicciones

Una contradicción puede impedir confirmar un campo.

El entregable debe conservar ese conflicto.

Define:

- Qué valores aparecen.
- Dónde aparecen.
- Qué campo afectan.
- Qué estado se asigna.
- Qué debe aclararse.

No elijas un valor solo por aparecer después.

La fuente puede establecer una regla de prioridad.

Si no la establece, documenta la incertidumbre.

El resto de la tarea puede continuar cuando sea seguro.

**Señalar un conflicto puede ser el resultado correcto.**

### 2.9. Criterios de aceptación

Los criterios permiten reconocer si la salida cumple.

Deben formularse antes de evaluar.

Ejemplos:

- Todos los campos obligatorios aparecen.
- Las cifras coinciden con la fuente.
- Las fechas tentativas no se confirman.
- Los valores ausentes no se inventan.
- Las propuestas se identifican.
- No se ejecutan acciones externas.

No todos los criterios requieren una puntuación.

Algunos pueden comprobarse con sí o no.

Otros necesitan una valoración justificada.

**Un criterio útil describe una propiedad observable.**

### 2.10. Matriz de comprobación

Relaciona cada criterio con una forma de verificarlo.

Esta matriz puede mantenerse fuera del prompt.

| Criterio | Método | Evidencia |
|---|---|---|
| Fidelidad | Comparar con la entrada | Fragmento de fuente |
| Completitud | Revisar campos | Lista de campos |
| Estado | Revisar condiciones | Verbos y notas |
| Formato | Revisar estructura | Salida guardada |
| Alcance | Buscar acciones no autorizadas | Fragmentos relevantes |

La matriz no debe convertirse en una lista automática sin lectura.

Un campo puede aparecer y ser incorrecto.

Comprueba contenido y estructura.

**La evaluación necesita evidencia, no solo casillas.**

### 2.11. Calidad del resultado y calidad del proceso

Una salida correcta no demuestra un proceso fiable.

Puede ser un resultado afortunado.

Un proceso documentado permite conocer sus condiciones.

Evalúa dos dimensiones:

- Calidad de la respuesta.
- Calidad de la revisión.

La primera incluye exactitud y utilidad.

La segunda incluye evidencia y trazabilidad.

Una respuesta errónea puede acompañarse de una revisión excelente.

Eso tiene valor formativo.

**El aprendizaje también consiste en reconocer cuándo no utilizar una salida.**

### 2.12. Indicadores de valor

Puedes proponer indicadores para evaluar el caso después.

Deben ser medibles y pertinentes.

Algunas opciones:

- Tiempo necesario para preparar una ficha.
- Número de correcciones.
- Campos correctamente extraídos.
- Errores relevantes detectados.
- Consistencia entre ejecuciones.
- Utilidad percibida por revisores.

La utilidad percibida no equivale a exactitud factual.

El tiempo debe incluir revisión y corrección.

No cuentes solo la generación.

**El coste total del trabajo incluye comprobar el resultado.**

### 2.13. Línea base y comparación

La línea base describe una situación inicial.

Puede ser un procedimiento manual o una primera versión del prompt.

No mezcles ambas comparaciones.

Comparar prompts muestra diferencias entre instrucciones.

Comparar con el proceso manual puede informar sobre el flujo completo.

Registra:

```text
Referencia inicial:
Condiciones:
Resultado:
Tiempo, si se ha medido:
Método de comprobación:
```

Una estimación debe identificarse como estimación.

**Las conclusiones dependen de qué comparación has realizado.**

### 2.14. Riesgos y controles

Cada riesgo debe relacionarse con una medida concreta.

No basta con escribir “la IA puede fallar”.

Ejemplo:

| Riesgo | Control inicial |
|---|---|
| Fecha inventada | Verificar contra la fuente |
| Dato sensible | Utilizar entrada sintética |
| Compromiso indebido | Excluir aprobación y envío |
| Contradicción ocultada | Conservar ambos valores |
| Formato incorrecto | Revisar campos o validar estructura |

El control puede reducir el riesgo sin eliminarlo.

Documenta quién lo aplica.

Algunos controles pertenecen a la aplicación, no al prompt.

**Una instrucción defensiva no constituye una protección completa.**

### 2.15. Ficha completa de definición

Utiliza esta estructura como documentación ampliada.

Durante la sesión podrás completar una versión más breve.

```text
NOMBRE DEL CASO
[Nombre descriptivo]

NECESIDAD
[Dificultad que se quiere reducir]

TAREA Y DESTINATARIO
[Acción, propósito y persona destinataria]

ENTRADA Y SALIDA
[Fuente disponible y resultado esperado]

ALCANCE
[Qué se incluye y qué se excluye]

EVALUACIÓN
[Criterios, métodos y evidencias]

RIESGOS Y SIGUIENTE PRUEBA
[Controles y primera comprobación]
```

## 3. Sesión práctica y ejemplos de aplicación

La sesión obligatoria termina con una ficha inicial.

Los ejemplos permiten practicar la definición sin exigir una implantación ni una evaluación completa en 30 minutos.

### 3.1. Agenda de la media hora

El tiempo se distribuye para favorecer una entrega concreta.

La ejecución de modelos no debe desplazar la definición.

| Minutos | Actividad | Resultado |
|---|---|---|
| 00–05 | Explicación y demostración | Referencia compartida |
| 05–10 | Selección de tarea | Caso elegido |
| 10–20 | Ficha mínima | Definición inicial |
| 20–27 | Revisión por parejas | Observaciones |
| 27–30 | Corrección y entrega | Versión 0.1 |

La ficha puede continuar desarrollándose después.

No se espera validar robustez durante esta sesión.

Si el grupo necesita más tiempo, omite la ejecución opcional.

**El resultado mínimo es una propuesta clara y revisable.**

### 3.2. Demostración del docente

El docente transforma una intención amplia en una tarea.

Puede utilizar este punto de partida:

```text
Quiero utilizar IA para gestionar formación.
```

Después delimita:

```text
Preparar una ficha interna a partir de un correo ficticio.

Extraer requisitos explícitos.
Señalar datos pendientes.
No enviar respuestas ni aprobar solicitudes.
```

El grupo observa qué ha cambiado.

Identifica tarea, entrada, salida y exclusiones.

La demostración no necesita ejecutar el prompt.

**La primera mejora consiste en definir mejor el trabajo.**

### 3.3. Seleccionar una opción

Elige una tarea del taller anterior o una alternativa sencilla.

Opciones recomendadas:

- Ficha de solicitud formativa.
- Resumen de informe.
- Extracción de acciones.
- Clasificación de solicitudes.
- Borrador de respuesta.
- Adaptación de contenido.

Si propones otro caso, comprueba su viabilidad.

Debe poder practicarse con datos sintéticos.

Debe tener una salida reconocible.

Debe permitir comprobar al menos tres criterios.

**No elijas una tarea solo porque parezca ambiciosa.**

### 3.4. Ficha mínima de la sesión

Completa esta plantilla.

Utiliza frases breves y específicas.

```text
Nombre del caso:

Necesidad que aborda:

Persona destinataria:

Tarea principal:

Entrada disponible:

Salida esperada:

Tres criterios de aceptación:

Principal riesgo y control:

Qué queda fuera:

Primera prueba:
```

Esta ficha constituye el entregable obligatorio de la unidad.

### 3.5. Ejemplo A: ficha de solicitud formativa

Este caso continúa el taller de prompts.

La necesidad es organizar requisitos antes de responder.

La destinataria es una persona coordinadora.

La tarea consiste en extraer información explícita.

La entrada será un correo ficticio.

La salida será una tabla con campos y estados.

El alcance excluye:

- Confirmar fechas.
- Presupuestar.
- Aprobar solicitudes.
- Enviar correos.

La revisión comprobará fidelidad, ausencia y estado.

**La ficha apoya la preparación de una respuesta, pero no la autoriza.**

### 3.6. Ejemplo A: entrada para practicar

Utiliza este correo sintético.

```text
ASUNTO: Consulta sobre una sesión

Hola:

Nos interesa una introducción a Prompt Engineering.
Participarán 12 personas del equipo administrativo.

Preferimos una sesión presencial de dos horas.
Proponemos el 18 de noviembre de 2026.
La fecha todavía no está confirmada.

Marta coordinará la solicitud.
No hemos definido el presupuesto.

Queremos utilizar únicamente ejemplos ficticios.

Gracias.
```

No añadas información externa para completar campos.

### 3.7. Ejemplo A: prompt inicial opcional

Este prompt puede utilizarse después de definir la ficha.

```text
Prepara una ficha interna a partir del correo.

Utiliza únicamente la fuente.
No inventes datos ni asumas compromisos.
Conserva la diferencia entre propuesta y confirmación.

Devuelve una tabla con:
- Campo.
- Valor.
- Estado.

Incluye tema, participantes, duración, modalidad,
fecha, persona coordinadora y presupuesto.

Si falta un dato, utiliza "No indicado".

CORREO
[Inserta aquí el correo completo]
```

Sustituye el marcador antes de ejecutar.

### 3.8. Ejemplo A: criterios y evidencia

Comprueba especialmente los estados.

La ficha debería conservar estas condiciones.

| Campo | Resultado verificable |
|---|---|
| Participantes | 12 |
| Duración | Dos horas solicitadas |
| Modalidad | Presencial preferida |
| Fecha | Propuesta, no confirmada |
| Coordinación | Marta |
| Presupuesto | Pendiente de definición |

Marta no aparece como docente.

El presupuesto no equivale a cero.

La fecha no autoriza una reserva.

**Una ficha estructurada puede contener errores operativos si pierde los estados.**

### 3.9. Ejemplo B: resumen de informe

Este caso busca preparar una lectura rápida.

La destinataria es una responsable de operaciones.

Utiliza esta entrada:

```text
INFORME SINTÉTICO

Se recibieron 120 solicitudes.
Se resolvieron 110.
Diez quedaron pendientes.

El tiempo medio de primera respuesta fue de 6 horas.
En el periodo anterior había sido de 8 horas.

No se dispone de satisfacción ni de costes.
Se propone analizar las causas de las solicitudes pendientes.
```

La salida será un resumen y una lista de datos pendientes.

**No debe confundirse primera respuesta con resolución.**

### 3.10. Ejemplo B: definición del entregable

Completa el caso con requisitos verificables.

La tarea será resumir el documento.

El alcance excluirá causas no documentadas.

Criterios recomendados:

- Mantener solicitudes recibidas y resueltas.
- Conservar el significado del tiempo.
- Identificar satisfacción y costes como ausentes.
- No afirmar mejoras no demostradas.
- Separar propuesta y resultado.

La primera prueba utilizará el informe completo.

Una segunda prueba podría eliminar un indicador.

Eso comprobaría el tratamiento de ausencia.

**Una sola salida correcta no demuestra estabilidad sobre otros informes.**

### 3.11. Ejemplo C: extracción de acciones

Este caso organiza notas de una reunión.

La salida ayuda a revisar compromisos.

Utiliza:

```text
NOTAS FICTICIAS

Ana enviará el borrador el 12 de noviembre.
El equipo revisará los indicadores.

No se ha asignado quién actualizará la plantilla.
Nos gustaría terminarla antes de la próxima reunión.

La próxima reunión será el 20 de noviembre.
No se ha fijado fecha límite para revisar indicadores.
```

La tabla tendrá acción, responsable y fecha.

No debe asignar responsables ausentes.

**La fecha de una reunión no es automáticamente una fecha límite.**

### 3.12. Ejemplo C: comprobación

Define una revisión campo por campo.

Criterios:

- Ana mantiene la acción del borrador.
- El 12 de noviembre se relaciona con el borrador.
- La plantilla queda sin responsable.
- La revisión de indicadores queda sin fecha límite.
- La preferencia temporal se conserva.

La evidencia debe incluir fragmentos de las notas.

No basta con una tabla aparentemente completa.

El riesgo principal es crear compromisos.

El control será la revisión humana antes de distribuir la ficha.

**Extraer acciones no autoriza asignar trabajo.**

### 3.13. Ejemplo D: clasificación de solicitudes

Este caso requiere reglas explícitas.

Utiliza estas entradas:

```text
S01: No puedo acceder al material.
S02: ¿Cuánto dura la sesión?
S03: Propongo añadir una práctica de correos.
S04: Necesito ayuda.
```

Define categorías:

- Incidencia.
- Información.
- Sugerencia.
- No determinada.

La salida incluirá identificador, categoría y evidencia.

La cuarta entrada debe permanecer ambigua.

**Una categoría de incertidumbre evita forzar precisión inexistente.**

### 3.14. Ejemplo E: borrador de respuesta

Este caso prepara texto sin enviarlo.

Utiliza esta solicitud:

```text
Hola:

Queremos información sobre una sesión online.
Participarán unas 20 personas.
Todavía no conocemos las fechas.

Necesitamos saber qué información debemos preparar.
```

El entregable será un borrador breve.

Debe confirmar recepción, no disponibilidad.

Debe conservar el número aproximado.

Debe solicitar datos pertinentes.

**El envío queda fuera del alcance y requiere autorización separada.**

### 3.15. Revisión por parejas y entrega

Intercambia la ficha mínima con otra persona.

La persona revisora debe responder estas preguntas.

- ¿Entiendo qué necesidad aborda?
- ¿La tarea es concreta?
- ¿La entrada está identificada?
- ¿La salida es reconocible?
- ¿Puedo comprobar los criterios?
- ¿Las exclusiones son claras?
- ¿El riesgo tiene un control?
- ¿La primera prueba es viable?

Anota una fortaleza y una mejora.

Corrige la ficha antes de entregarla.

No necesitas aceptar comentarios que contradigan la tarea.

**La revisión debe mejorar claridad y verificabilidad, no ampliar el proyecto sin motivo.**

## 4. Evaluación, documentación y continuidad del curso

La ficha inicial será una referencia para técnicas, pruebas y revisiones posteriores.

Su valor consiste en mantener conectado el aprendizaje con una tarea concreta.

### 4.1. Entregable obligatorio de la unidad

Entrega la ficha mínima revisada.

Debe poder leerse sin consultar la conversación completa.

Incluye:

1. Nombre del caso.
2. Necesidad.
3. Persona destinataria.
4. Tarea.
5. Entrada.
6. Salida.
7. Tres criterios.
8. Riesgo y control.
9. Exclusiones.
10. Primera prueba.

La ejecución del prompt es un anexo opcional.

**La ausencia de una ejecución no invalida una definición completa.**

### 4.2. Qué todavía no se exige

Esta media hora no requiere un proyecto terminado.

No se exige:

- Automatización.
- Uso de API.
- Integración con servicios.
- Mediciones completas.
- Evaluación estadística.
- Biblioteca extensa de prompts.
- Validación de producción.

Tampoco se exige una promesa de ahorro.

La propuesta puede contener preguntas pendientes.

Debe reconocerlas.

**Una definición inicial es un punto de partida, no una certificación de fiabilidad.**

### 4.3. Rúbrica formativa

La rúbrica ayuda a identificar mejoras.

Debe aplicarse leyendo la ficha.

| Dimensión | Inicial | Adecuada | Clara y verificable |
|---|---|---|---|
| Necesidad | General | Reconocible | Conectada con una actividad |
| Tarea | Amplia | Delimitada | Alcance y exclusiones claros |
| Datos | No definidos | Identificados | Disponibles y seguros |
| Salida | Vaga | Reconocible | Campos y uso definidos |
| Evaluación | Subjetiva | Criterios presentes | Métodos comprobables |

No se premia complejidad técnica.

Una tarea sencilla puede alcanzar el nivel más claro.

Los comentarios deben indicar una acción de mejora.

**La evaluación reconoce la calidad de la definición.**

### 4.4. Checklist de aceptación

Revisa la ficha antes de enviarla.

Marca únicamente lo que puedas demostrar.

- [ ] La necesidad está descrita.
- [ ] La tarea tiene una acción principal.
- [ ] El destinatario está identificado.
- [ ] Los datos son utilizables.
- [ ] La salida está definida.
- [ ] Hay tres criterios verificables.
- [ ] El alcance es razonable.
- [ ] Las exclusiones están visibles.
- [ ] El riesgo tiene un control.
- [ ] La primera prueba es viable.
- [ ] No se afirman beneficios no medidos.

**Las casillas no sustituyen la lectura crítica.**

### 4.5. Organización recomendada de archivos

Mantén una estructura sencilla.

No necesitas herramientas especiales.

Ejemplo:

```text
caso-de-uso/
├── ficha-caso.md
├── datos/
│   └── caso-sintetico-01.txt
├── prompts/
│   └── prompt-v0.1.txt
├── resultados/
│   └── respuesta-01.txt
└── evaluacion/
    └── registro-pruebas.md
```

Durante esta unidad basta con `ficha-caso.md`.

Las carpetas adicionales pueden completarse después.

**La estructura debe facilitar localizar evidencias.**

### 4.6. Registro de versiones

La ficha también puede evolucionar.

Registra cambios de alcance y evaluación.

| Versión | Cambio | Motivo |
|---|---|---|
| 0.1 | Definición inicial | Cierre del 1 |
| 0.2 | Ajuste de formato | Necesidad del destinatario |
| 0.3 | Nuevo caso de prueba | Evaluar información ausente |

No necesitas crear versiones por correcciones tipográficas menores.

Sí conviene registrar cambios que afectan al trabajo.

La versión del caso y la del prompt pueden ser diferentes.

Relaciona ambas cuando guardes pruebas.

**Versionar evita perder el motivo de las decisiones.**

### 4.7. Primera prueba documentada

Cuando ejecutes el caso, registra sus condiciones.

Utiliza esta plantilla:

```text
Identificador:
Fecha:
Versión del caso:
Versión del prompt:
Plataforma y modelo visible:
Entrada utilizada:

Resultado:
Criterios cumplidos:
Criterios incumplidos:

Evidencia:
Limitación:
Siguiente comprobación:
```

Conserva también la salida original.

### 4.8. Separar observación e interpretación

Una observación describe lo que ocurrió.

Una interpretación explica qué puede significar.

Ejemplo:

```text
Observación:
La respuesta marcó la fecha propuesta como confirmada.

Interpretación:
El tratamiento del estado no fue suficiente en esta prueba.

No demostrado:
Que el sistema falle siempre con fechas tentativas.
```

Esta separación evita conclusiones excesivas.

También facilita decidir la siguiente comprobación.

No atribuyas una causa interna sin evidencia.

**Describe primero el comportamiento observable.**

### 4.9. Casos de prueba posteriores

El caso elegido debe admitir variaciones pertinentes.

Puedes preparar:

- Una entrada completa.
- Una entrada incompleta.
- Una entrada contradictoria.
- Una entrada ambigua.
- Una entrada con contenido irrelevante.
- Una entrada con instrucciones incrustadas.

No todas las variaciones aplican a cualquier tarea.

Selecciona las que representan riesgos reales.

Los resultados esperados deben definirse antes de ejecutar.

Evita adaptar la evaluación para favorecer una salida.

**La diversidad de pruebas debe responder al propósito del caso.**

### 4.10. Límites de las pruebas pequeñas

Un conjunto reducido permite observar comportamientos.

No permite demostrar fiabilidad general.

Tampoco representa necesariamente los datos reales.

Una prueba del curso puede mostrar:

- Viabilidad inicial.
- Un fallo concreto.
- Cumplimiento de requisitos.
- Necesidad de reformulación.
- Una mejora local.

No demuestra ausencia de errores futuros.

La conclusión debe mencionar su alcance.

Una ejecución exitosa no elimina la revisión.

**Evidencia limitada exige afirmaciones limitadas.**

### 4.11. Continuidad durante las cinco jornadas

El caso inicial puede acompañarte durante el curso.

Cada jornada añadirá una perspectiva.

| Jornada | Evolución del caso |
|---|---|
| 1 | Definición y línea base |
| 2 | Técnicas y formatos |
| 3 | Evaluación y seguridad |
| 4 | Adaptación a una aplicación |
| 5 | Consolidación del proyecto |

El caso puede reformularse si deja de ser viable.

Documenta por qué cambias.

No mantengas una propuesta inadecuada solo por haberla elegido primero.

La continuidad debe apoyar aprendizaje.

**Evolucionar el alcance también es una decisión válida.**

### 4.12. Paso al proyecto final

La ficha inicial será una base, no el proyecto completo.

El proyecto incorporará evidencias adicionales según sus instrucciones.

Habitualmente necesitará:

- Definición revisada.
- Prompts versionados.
- Datos de prueba.
- Resultados originales.
- Evaluación.
- Riesgos.
- Limitaciones.
- Recomendaciones de uso.

Consulta los requisitos específicos del proyecto.

No supongas que esta ficha sustituye todos los entregables posteriores.

**El proyecto demuestra una evolución documentada.**

### 4.13. Orientaciones para el docente

Prioriza claridad y viabilidad.

Evita que la sesión se transforme en una discusión sobre herramientas.

Intervenciones útiles:

- “¿Qué trabajo concreto quieres completar?”
- “¿Quién utilizará la salida?”
- “¿Qué dato necesitas para probarlo?”
- “¿Cómo reconocerás un error?”
- “¿Qué queda fuera?”
- “¿Qué puedes entregar en el tiempo disponible?”

Ayuda a reducir propuestas demasiado amplias.

No impongas ejecución si perjudica la definición.

Utiliza los ejemplos como referencias adaptables.

**El cierre debe producir una ficha, no una promesa vaga.**

### 4.15. Ideas esenciales para avanzar

Un caso de uso comienza con una necesidad concreta.

La tarea debe tener un alcance reconocible.

La entrada debe ser disponible, pertinente y segura.

La salida necesita un destinatario y un propósito.

El entregable funcional es distinto de la evidencia académica.

Los criterios deben permitir comprobación.

Los riesgos necesitan controles.

La primera prueba debe ser pequeña y viable.

Las expectativas no equivalen a beneficios demostrados.

Las limitaciones forman parte de una documentación honesta.
