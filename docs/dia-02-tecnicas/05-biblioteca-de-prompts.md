# Biblioteca de prompts

Una biblioteca de prompts reúne instrucciones documentadas que pueden localizarse, adaptarse y utilizarse con criterios conocidos.

No es únicamente una colección de mensajes que alguna vez produjeron una respuesta satisfactoria.

Su valor depende de que cada entrada explique para qué sirve, qué necesita y cómo se comprueba.

También debe mostrar qué limitaciones tiene y cuándo no conviene utilizarla.

Esta unidad cierra la segunda jornada del curso.

Durante la sesión organizarás parte del trabajo realizado en las unidades anteriores.

Seleccionarás prompts, completarás sus fichas y prepararás una estructura sencilla de consulta.

No necesitas crear un catálogo extenso.

Necesitas construir una primera biblioteca que otra persona pueda comprender sin reconstruir tus conversaciones.

La biblioteca podrá evolucionar durante las jornadas de evaluación, seguridad y proyecto final.

**Reutilizar un prompt significa recuperar un diseño documentado, adaptarlo y comprobar que sigue siendo adecuado.**

!!! info "Duración y alcance"
    La sesión lectiva dura 30 minutos.
    Esta página incluye documentación ampliada y prácticas opcionales.
    Durante la sesión se organizan tres entradas ya trabajadas.
    No se exige ejecutar de nuevo todos los prompts ni validar una biblioteca para producción.

## 1. Fundamentos: de una colección de mensajes a una biblioteca útil

Esta sección explica qué debe contener una biblioteca y qué problemas ayuda a resolver.

El objetivo es conservar decisiones y evidencias, no acumular instrucciones sin contexto.

### 1.1. Ficha de la unidad

La unidad integra el trabajo del segundo día.

| Elemento | Descripción |
|---|---|
| Jornada | 2 · Técnicas y formatos |
| Unidad | Biblioteca de prompts |
| Duración lectiva | 0,5 horas |
| Modalidad | Explicación, demostración y práctica |
| Resultado | Biblioteca inicial con tres entradas |

Se requiere disponer de prompts elaborados anteriormente.

Pueden proceder del 1 o del 2.

No se requiere programación.

Un editor de texto y una carpeta son suficientes.

También puede utilizarse un documento compartido autorizado.

Las evidencias deben permanecer accesibles.

**La prioridad es organizar y documentar, no generar más contenido.**

### 1.2. Objetivos de aprendizaje

Los objetivos describen acciones que podrás demostrar.

Al finalizar podrás:

- Distinguir una colección informal y una biblioteca documentada.
- Seleccionar prompts adecuados para conservar.
- Asignar identificadores y nombres descriptivos.
- Separar plantillas y ejemplos completados.
- Identificar variables y restricciones.
- Relacionar versiones con evidencias.
- Registrar estados de evaluación.
- Localizar limitaciones antes de reutilizar.
- Preparar un índice navegable.
- Documentar una primera decisión de mantenimiento.

No necesitas dominar herramientas de gestión documental.

Sí necesitas que la organización sea comprensible.

**La biblioteca debe facilitar una consulta responsable.**

### 1.3. Qué es una biblioteca de prompts

Una biblioteca es un conjunto organizado de entradas relacionadas con tareas.

Cada entrada contiene una instrucción y la información necesaria para utilizarla.

Puede incluir:

- Propósito.
- Destinatario.
- Datos de entrada.
- Variables.
- Formato de salida.
- Criterios de aceptación.
- Evidencias.
- Limitaciones.
- Historial de cambios.

La organización permite recuperar una entrada por su función.

No depende de recordar cuándo se utilizó.

**El prompt es una parte de la entrada, no toda la entrada.**

### 1.4. Qué no es una biblioteca

Una biblioteca no debería confundirse con un archivo indiscriminado.

No basta con guardar capturas de conversaciones.

Tampoco basta con copiar instrucciones de distintas procedencias.

Problemas de una colección informal:

- Nombres poco descriptivos.
- Prompts sin fuentes.
- Versiones mezcladas.
- Variables sin explicar.
- Respuestas corregidas sin registro.
- Ausencia de criterios.
- Estado de evaluación desconocido.
- Datos sensibles incorporados.

Una colección puede servir como punto de partida.

Necesita revisión antes de presentarse como biblioteca reutilizable.

**Guardar contenido no equivale a documentar su uso.**

### 1.5. Qué problema resuelve

Una biblioteca reduce la necesidad de reconstruir decisiones anteriores.

Permite localizar diseños ya trabajados.

También ayuda a compartir una metodología.

Puede facilitar:

- Consistencia.
- Trazabilidad.
- Revisión.
- Adaptación.
- Transferencia entre personas.
- Identificación de errores recurrentes.
- Actualización de instrucciones.

Estos beneficios son expectativas razonables.

Su magnitud debe medirse si se desea demostrar ahorro o eficiencia.

No afirmes mejoras que no has observado.

**La biblioteca organiza conocimiento de trabajo; su valor real depende del uso.**

### 1.6. Prompt, plantilla y ejemplo

Estos tres elementos deben distinguirse.

Un prompt ejecutable contiene una tarea concreta y sus datos.

Una plantilla contiene espacios que deben completarse.

Un ejemplo muestra una aplicación de la plantilla.

| Elemento | Función |
|---|---|
| Plantilla | Facilitar adaptación |
| Prompt completado | Ejecutar una tarea específica |
| Ejemplo de salida | Mostrar una respuesta o referencia |

Un marcador pendiente puede impedir una ejecución correcta.

Un ejemplo no debe confundirse con información real.

Identifica si la salida procede de una ejecución o fue redactada para enseñar.

No conviertas un único ejemplo en garantía de comportamiento.

**La separación evita reutilizaciones accidentales.**

### 1.7. Entrada y caso de uso

Una entrada puede apoyar una parte de un caso de uso.

Un caso de uso puede necesitar varias entradas.

Por ejemplo:

```text
Caso de uso:
Preparar una respuesta a una solicitud de formación.

Entradas de biblioteca:
- Extraer requisitos.
- Detectar pendientes.
- Redactar un borrador.
- Revisar compromisos.
```

No es obligatorio separar todas esas funciones.

La decisión depende de complejidad y riesgo.

Documenta las relaciones si existen.

**La biblioteca debe reflejar el trabajo, no fragmentarlo por costumbre.**

### 1.8. Biblioteca personal y compartida

Una biblioteca personal puede utilizar convenciones sencillas.

Una biblioteca compartida necesita explicaciones más explícitas.

Otras personas no conocen tus supuestos.

Conviene definir:

- Quién mantiene las entradas.
- Quién puede modificarlas.
- Cómo se revisan cambios.
- Qué significan los estados.
- Dónde están las evidencias.
- Cómo se registra un incidente.
- Qué usos están excluidos.

No necesitas una estructura empresarial para comenzar.

Sí necesitas evitar responsabilidades implícitas.

**Cuantas más personas reutilicen, más importante es la claridad documental.**

### 1.9. Reutilización y adaptación

Reutilizar no significa copiar y enviar sin leer.

Antes de utilizar una entrada, comprueba su pertinencia.

Revisa:

- Tarea.
- Destinatario.
- Fuente.
- Variables.
- Herramientas.
- Formato.
- Riesgo.
- Estado de evaluación.

Una nueva entrada puede introducir dificultades no probadas.

Un nuevo modelo puede comportarse de otra manera.

La adaptación puede requerir una nueva versión.

**La reutilización responsable incluye una comprobación de condiciones.**

### 1.10. Estado documental y calidad

Un estado resume la situación de una entrada.

No debería prometer más de lo que se ha evaluado.

Utilizaremos estos estados didácticos:

- Borrador.
- Probado en casos documentados.
- En revisión.
- Retirado.

“Probado” no significa “fiable para cualquier entrada”.

Tampoco significa “preparado para producción”.

Debe acompañarse de la descripción de las pruebas.

Si falta evidencia, conserva el estado de borrador.

No deduzcas calidad a partir del nombre del archivo.

**El estado debe remitir a evidencia, no sustituirla.**

### 1.11. Riesgos de una biblioteca mal mantenida

Una biblioteca puede amplificar errores si facilita reutilizarlos.

Los riesgos incluyen:

- Instrucciones desactualizadas.
- Ejemplos incorrectos.
- Datos privados en plantillas.
- Formatos incompatibles.
- Promesas de capacidad inexistente.
- Dependencias no documentadas.
- Versiones antiguas tomadas como actuales.
- Criterios omitidos.

La buena organización no elimina estos riesgos.

Permite detectarlos y gestionarlos mejor.

La revisión debe tener responsables y motivos.

**Una entrada popular también puede necesitar corrección o retirada.**

### 1.12. Principio de mínima biblioteca útil

No necesitas conservar todo lo que has escrito.

Empieza con pocas entradas y documentación suficiente.

Una biblioteca inicial útil contiene:

- Un índice.
- Tres entradas distintas.
- Variables explicadas.
- Restricciones visibles.
- Evidencias localizables.
- Limitaciones.
- Versiones identificadas.

Es preferible tener tres entradas revisables que treinta ambiguas.

La ampliación debe responder a necesidades.

Evita duplicar por cambios menores de redacción.

**La utilidad depende de recuperar y comprender, no del tamaño del catálogo.**

## 2. Diseño documental: fichas, variables, versiones y evidencias

Esta sección establece una estructura reutilizable para las entradas.

El diseño puede implementarse con archivos Markdown, documentos o herramientas de gestión autorizadas.

### 2.1. Seleccionar entradas para conservar

Selecciona tareas que ya hayas trabajado.

No necesitas que todas hayan funcionado perfectamente.

Una entrada con fallos conocidos puede conservarse como borrador.

Criterios de selección:

- Propósito reconocible.
- Posibilidad de reutilización.
- Fuente o entrada definida.
- Resultado esperado.
- Criterios de comprobación.
- Evidencia disponible.
- Limitaciones identificadas.

No selecciones únicamente respuestas vistosas.

Prioriza tareas que puedas explicar y revisar.

**La selección es una decisión de utilidad y trazabilidad.**

### 2.2. Asignar un identificador estable

El identificador permite relacionar documentos y evidencias.

Debe mantenerse aunque cambie el título.

Una convención sencilla es:

```text
P-001
P-002
P-003
```

La versión se registra por separado.

No conviertas la fecha en el único identificador.

Evita reutilizar identificadores retirados.

Si divides una entrada, crea nuevas referencias.

Si fusionas entradas, registra de dónde proceden.

No necesitas una codificación compleja.

**La estabilidad facilita seguir la evolución.**

### 2.3. Elegir nombres descriptivos

El nombre debe expresar qué trabajo realiza la entrada.

Ejemplos adecuados:

- Extraer requisitos de una solicitud.
- Resumir un informe operativo.
- Preparar un borrador sin compromisos.
- Clasificar solicitudes con reglas.
- Revisar fechas y estados.

Evita nombres como:

- Prompt perfecto.
- Superexperto.
- El mejor.
- Final definitivo.
- Funciona siempre.

El nombre no debe prometer rendimiento.

Puede indicar el dominio cuando sea relevante.

**Nombrar bien facilita localizar sin abrir todos los archivos.**

### 2.4. Organizar categorías y etiquetas

Las categorías agrupan funciones generales.

Las etiquetas añaden atributos de búsqueda.

Una organización posible es:

| Categoría | Etiquetas de ejemplo |
|---|---|
| Extracción | correo, requisitos, ausencias |
| Síntesis | informe, resumen, indicadores |
| Redacción | borrador, tono, comunicación |
| Revisión | contradicciones, alcance, evidencias |

Mantén un vocabulario pequeño al comenzar.

Evita etiquetas equivalentes con nombres distintos.

“Correo” y “email” pueden duplicar búsquedas.

Define la convención elegida.

No incluyas información privada en etiquetas.

**La clasificación debe facilitar consulta, no añadir burocracia.**

### 2.5. Crear una ficha mínima

La ficha reúne decisiones esenciales.

Puede utilizar esta estructura:

```text
ID:
Nombre:
Versión:
Estado:

Propósito:
Destinatario:
Entrada:
Salida:

Variables:
Restricciones:
Criterios:

Evidencias:
Limitaciones:
Responsable:
```

### 2.6. Documentar el propósito

El propósito explica por qué existe la entrada.

No debe limitarse a nombrar la tecnología.

Compara:

```text
Propósito general:
Usar IA para operaciones.

Propósito concreto:
Preparar una ficha interna con requisitos explícitos
de un correo, antes de redactar una respuesta.
```

El propósito concreto orienta criterios y exclusiones.

También ayuda a detectar usos impropios.

No necesitas prometer automatización.

Un apoyo parcial puede ser suficiente.

**La entrada debe facilitar una actividad identificable.**

### 2.7. Definir la entrada

Describe qué material puede procesarse.

Especifica cuando sea relevante:

- Tipo de documento.
- Idioma.
- Estructura.
- Longitud orientativa.
- Procedencia autorizada.
- Presencia de tablas.
- Condiciones de privacidad.
- Información mínima necesaria.

No inventes límites de la plataforma.

Si hay restricciones técnicas, compruébalas.

Si todavía no hay muestras reales, indícalo.

**La entrada documentada debe corresponder a lo evaluado.**

### 2.8. Definir la salida

La salida debe tener un destinatario o consumidor.

Describe su estructura.

Puedes especificar:

- Secciones.
- Campos.
- Orden.
- Tipos.
- Extensión.
- Valores permitidos.
- Ausencias.
- Texto adicional permitido.

“Análisis completo” no define suficiente contenido.

“JSON” no define un esquema.

Una salida humana y una salida automática necesitan controles distintos.

**El formato debe responder al uso posterior.**

### 2.9. Identificar variables

Las variables representan información que cambia.

Utilizaremos marcadores visibles:

```text
{{DOCUMENTO}}
{{DESTINATARIO}}
{{EXTENSION_MAXIMA}}
{{CATEGORIAS}}
```

Estos marcadores son una convención documental.

No se sustituyen automáticamente en todas las interfaces.

Explica cómo completar cada uno.

No permitas que una variable cambie reglas críticas sin revisión.

Evita marcadores con nombres ambiguos.

Comprueba que no queden pendientes antes de ejecutar.

**Una variable debe tener significado y condiciones de uso.**

### 2.10. Separar variables y restricciones

No todo lo editable debería tratarse como variable libre.

Las restricciones mantienen límites del diseño.

Ejemplos de restricciones:

- Utilizar únicamente la fuente.
- No inventar datos.
- Conservar propuestas como propuestas.
- No enviar respuestas.
- No aprobar solicitudes.
- Señalar contradicciones.

Cambiar una restricción puede alterar el caso de uso.

Ese cambio requiere revisión.

No lo presentes como una adaptación trivial.

Las variables también pueden tener límites.

**La facilidad de edición no debe eliminar controles importantes.**

### 2.11. Documentar dependencias

Una dependencia es una condición externa necesaria.

Puede ser:

- Una fuente.
- Una herramienta.
- Un esquema.
- Un catálogo de categorías.
- Una calculadora.
- Una revisión especializada.
- Una versión de plantilla.

La entrada debe indicar si la dependencia está disponible.

No atribuyas búsqueda a un prompt sin herramienta.

No atribuyas cálculo verificado a texto generado sin comprobación.

Cuando una dependencia cambia, puede necesitarse reevaluación.

Mantén enlaces localizables.

**Una instrucción no crea por sí sola recursos ni permisos.**

### 2.12. Diseñar criterios de aceptación

Los criterios describen propiedades observables.

Ejemplos:

- Todos los campos obligatorios aparecen.
- Los números coinciden con la fuente.
- Las aproximaciones permanecen visibles.
- Las fechas propuestas no se confirman.
- Las ausencias no se convierten en cero.
- El formato cumple el esquema.
- No aparecen compromisos no autorizados.

Define cómo comprobar cada criterio.

No mezcles aceptación y preferencias sin distinguirlas.

Un tono más amable no compensa un dato incorrecto.

Los criterios pueden variar entre entradas.

**La evaluación debe responder a la tarea concreta.**

### 2.13. Asociar casos de prueba

Una entrada debe relacionarse con sus pruebas.

Utiliza identificadores independientes.

Ejemplo:

```text
P-001
Casos:
- C01: solicitud completa.
- C02: participantes aproximados.
- C03: fecha propuesta.
- C04: datos ausentes.
- C05: valores contradictorios.
```

No todos los casos se necesitan en la sesión.

Los casos pendientes deben identificarse.

No incluyas respuestas reservadas dentro de ejemplos ejecutados.

Conserva referencias por separado.

**El catálogo de pruebas muestra qué se ha explorado y qué falta.**

### 2.14. Registrar evidencias

Una evidencia debe permitir reconstruir una comprobación.

Conserva:

- Entrada utilizada.
- Prompt completo.
- Versión.
- Entorno conocido.
- Respuesta original.
- Referencia.
- Evaluación.
- Corrección, si existe.

No guardes solo la respuesta final editada.

No presentes una salida simulada como ejecución.

Relaciona la evidencia con el caso.

Evita enlaces que otras personas no pueden abrir.

**La biblioteca debe facilitar revisar el fundamento de sus estados.**

### 2.15. Versionar cambios

Una versión identifica un diseño concreto.

Puedes utilizar una convención sencilla.

```text
0.1: primera ficha.
0.2: tratamiento de fechas añadido.
0.3: esquema de salida modificado.
```

Los números no certifican madurez.

Una versión denominada `1.0` tampoco garantiza producción.

Define la convención de la biblioteca.

Registra cambios que afectan al comportamiento.

No necesitas una versión por cada corrección tipográfica.

Mantén versiones anteriores localizables.

**La versión debe explicar qué se utilizó en una prueba.**

### 2.16. Historial y retirada

El historial registra decisiones relevantes.

Incluye:

- Fecha.
- Versión.
- Cambio.
- Motivo.
- Evidencia.
- Responsable.

Una entrada retirada puede conservarse como referencia histórica.

Debe indicar por qué no se recomienda su uso.

No la borres automáticamente si sostiene una evaluación anterior.

Añade una alternativa cuando exista.

No sustituyas el archivo sin dejar rastro.

**Retirar también es una decisión de mantenimiento.**

## 3. Sesión práctica: construir una biblioteca inicial de tres entradas

La práctica obligatoria organiza material ya elaborado.

No exige repetir el laboratorio comparativo ni ejecutar todos los ejemplos de esta página.

### 3.1. Agenda de los 30 minutos

La sesión debe terminar con una estructura consultable.

La ejecución de modelos es opcional.

| Minutos | Actividad | Resultado |
|---|---|---|
| 00–05 | Explicación y demostración | Referencia común |
| 05–10 | Selección de tres entradas | Catálogo inicial |
| 10–20 | Fichas y archivos | Biblioteca organizada |
| 20–27 | Revisión por parejas | Incidencias |
| 27–30 | Corrección y entrega | Versión inicial |

Utiliza evidencias que ya tengas.

No inventes pruebas para completar campos.

Si falta algo, marca pendiente.

Prioriza claridad y localización.

**El mínimo es una biblioteca pequeña y honesta sobre su estado.**

### 3.2. Preparar el material

Localiza tres prompts del curso.

Pueden corresponder a:

- Resumen.
- Extracción.
- Clasificación.
- Redacción.
- Revisión.
- Transformación estructurada.

Recupera también sus entradas y respuestas.

Si una respuesta falta, indícalo.

No ejecutes automáticamente para rellenar sin tiempo de revisión.

Comprueba que no haya datos sensibles.

Distingue originales y correcciones.

**La preparación evita convertir la sesión en una búsqueda de archivos.**

### 3.3. Seleccionar tres tareas diferentes

Elige entradas con funciones reconocibles.

Una propuesta de selección es:

```text
P-001:
Extraer requisitos de una solicitud.

P-002:
Resumir un informe operativo.

P-003:
Preparar un borrador sin compromisos.
```

No necesitas utilizar esos mismos nombres.

Evita tres versiones casi idénticas de una tarea.

Puedes conservar variantes dentro de una entrada.

La selección debe aportar variedad funcional.

**Tres funciones diferentes muestran mejor la estructura de la biblioteca.**

### 3.4. Crear la estructura de carpetas

Utiliza una organización sencilla.

Ejemplo:

```text
biblioteca/
├── index.md
├── entradas/
│   ├── P-001-extraccion.md
│   ├── P-002-resumen.md
│   └── P-003-borrador.md
├── casos/
└── evidencias/
```

Los nombres son una propuesta.

Puedes utilizar un documento único equivalente.

No crees carpetas vacías innecesarias si dificultan el trabajo.

Añade rutas cuando tengas contenido.

**La estructura debe facilitar encontrar, no impresionar.**

### 3.5. Construir el índice

El índice permite consultar sin abrir todas las fichas.

Incluye información breve.

Ejemplo:

| ID | Entrada | Versión | Estado |
|---|---|---|---|
| P-001 | Extracción de requisitos | 0.1 | Registrar estado real |
| P-002 | Resumen operativo | 0.1 | Registrar estado real |
| P-003 | Borrador de respuesta | 0.1 | Registrar estado real |

Enlaza cada nombre con su archivo.

No incluyas estados favorables sin evidencia.

Añade una explicación de los estados.

Puede incluir categorías o etiquetas después.

Revisa que los enlaces funcionen.

**El índice debe mostrar qué existe y cómo localizarlo.**

### 3.6. Entrada P-001: definición

Esta entrada organiza requisitos de un correo.

Su propósito es apoyar una revisión interna.

Ficha de referencia:

```text
ID: P-001
Nombre: Extraer requisitos de una solicitud
Versión: 0.1
Estado: Borrador hasta incorporar evidencias

Destinatario: coordinación
Entrada: correo sintético o autorizado
Salida: tabla de campos, valores y estados
Categoría: extracción
Etiquetas: correo, requisitos, ausencias
```

Completa responsable y evidencias reales.

**El estado del ejemplo no describe automáticamente tu trabajo.**

### 3.7. Entrada P-001: plantilla

Esta plantilla debe completarse antes de ejecutar.

No incluye herramientas externas.

```text
Prepara una ficha interna de requisitos.

Utiliza únicamente el correo.
No inventes datos ni asumas compromisos.
Conserva aproximaciones, preferencias y propuestas.

Devuelve una tabla con campo, valor y estado.
Incluye tema, participantes, modalidad, duración,
fecha, coordinación, aula y presupuesto.

Si falta un dato, escribe "No indicado".
Si está pendiente, conserva ese estado.
Si hay contradicción, señala los valores.

CORREO
{{CORREO}}
```

### 3.8. Entrada P-001: variable

La variable debe tener instrucciones de uso.

Documenta:

```text
Variable: {{CORREO}}

Contenido:
Texto completo de una solicitud.

Condiciones:
Sin credenciales ni datos sensibles.
Conservar notas que afecten a estados.
No sustituir por un resumen no revisado.

Comprobación previa:
El marcador se ha reemplazado.
La procedencia permite su uso.
```

Si utilizas adjuntos, verifica su disponibilidad.

**La variable define qué entra, no solo dónde pegar texto.**

### 3.9. Entrada P-001: caso sintético

Utiliza este caso como referencia de práctica.

No es una solicitud real.

```text
Queremos una introducción a Prompt Engineering.

Participarán aproximadamente 12 personas.
Preferimos modalidad presencial durante dos horas.

Proponemos el 18 de noviembre de 2026.
La fecha todavía no está confirmada.

Laura coordinará la solicitud.
El aula está pendiente.
No hemos definido el presupuesto.
```

Guárdalo con un identificador propio.

No lo mezcles con el texto de la plantilla.

**La separación facilita probar variantes.**

### 3.10. Entrada P-001: comprobación

La ficha debe conservar estos elementos.

Criterios:

- Participantes: aproximadamente 12.
- Modalidad: preferencia presencial.
- Duración: dos horas solicitadas.
- Fecha: propuesta.
- Coordinación: Laura.
- Aula: pendiente.
- Presupuesto: no definido.

Laura no aparece como docente.

El presupuesto no equivale a cero.

La fecha no autoriza reserva.

Registra el método: comparación con el correo.

**El valor y el estado deben revisarse juntos.**

### 3.11. Entrada P-002: definición

Esta entrada prepara una lectura rápida de un informe.

No demuestra causas ni rendimiento general.

Ficha de referencia:

```text
ID: P-002
Nombre: Resumir un informe operativo
Versión: 0.1
Estado: Borrador hasta incorporar evidencias

Destinatario: responsable de operaciones
Entrada: informe con indicadores explícitos
Salida: resumen, hallazgos y datos pendientes
Categoría: síntesis
Etiquetas: informe, indicadores, fidelidad
```

Indica si admite cálculos adicionales.

**La política de cálculo debe estar documentada.**

### 3.12. Entrada P-002: plantilla

Esta versión no solicita cálculos nuevos.

Utiliza únicamente los datos del informe.

```text
Resume el informe para {{DESTINATARIO}}.

Utiliza únicamente la fuente.
Conserva cifras, unidades, periodos y significado.
No atribuyas causas ni mejoras no documentadas.
No añadas cálculos que no se solicitan.
Identifica la información no disponible.

Devuelve:
- Resumen de hasta {{LIMITE_PALABRAS}} palabras.
- Tres hallazgos.
- Datos pendientes.
- Próximo paso propuesto en la fuente.

INFORME
{{INFORME}}
```

### 3.13. Entrada P-002: variables

Explica cada variable antes de reutilizar.

Documenta:

- `{{DESTINATARIO}}`: función y conocimientos relevantes.
- `{{LIMITE_PALABRAS}}`: entero positivo adecuado al uso.
- `{{INFORME}}`: documento completo que debe resumirse.

El límite debe permitir conservar información crítica.

Si es incompatible, revisa el diseño.

No inventes capacidades de procesamiento.

No introduzcas un destinatario que cambie el alcance sin revisión.

Si el conteo es estricto, compruébalo por separado.

Las variables no deben modificar la fuente.

Guarda el prompt completado de cada prueba.

**La plantilla y su instancia son evidencias distintas.**

### 3.14. Entrada P-002: caso sintético

Este informe permite revisar fidelidad.

No contiene una explicación causal.

```text
Se recibieron 120 solicitudes.
Se resolvieron 110.
Diez quedaron pendientes.

El tiempo medio de primera respuesta fue de 6 horas.
En el periodo anterior había sido de 8 horas.

No se dispone de satisfacción ni de costes.

Se propone analizar las causas de los pendientes.
```

El indicador es primera respuesta.

No debe convertirse en tiempo de resolución.

**Una cifra correcta puede acompañar un concepto incorrecto.**

### 3.15. Entrada P-002: comprobación

Define criterios concretos.

Comprueba:

- Conserva 120 recibidas.
- Conserva 110 resueltas.
- Conserva 10 pendientes.
- Habla de primera respuesta.
- Mantiene comparación de 6 y 8 horas.
- Identifica satisfacción ausente.
- Identifica costes ausentes.
- Separa propuesta y resultado.

No debe afirmar satisfacción mejorada.

No debe inventar causas.

Si añade un cálculo, registra incumplimiento de esta plantilla.

**Evalúa el diseño elegido, no toda información que podría ser útil.**

### 3.16. Entrada P-003: definición

Esta entrada redacta un borrador revisable.

El envío queda fuera del alcance.

Ficha de referencia:

```text
ID: P-003
Nombre: Preparar un borrador sin compromisos
Versión: 0.1
Estado: Borrador hasta incorporar evidencias

Destinatario: persona solicitante
Entrada: correo y límites de respuesta
Salida: borrador de correo
Categoría: redacción
Etiquetas: comunicación, tono, alcance
```

Relaciona P-001 si utilizas una ficha previa.

**Las dependencias deben quedar visibles.**

### 3.17. Entrada P-003: plantilla

Esta plantilla permite adaptar el lenguaje.

No concede autorización comercial.

```text
Redacta un borrador de respuesta al correo.

Utiliza un tono profesional, cercano y directo.
Confirma únicamente la recepción.
Resume los requisitos explícitos.
Conserva aproximaciones y condiciones pendientes.
Formula hasta tres preguntas pertinentes.

No confirmes disponibilidad, precios ni contratación.
No inventes servicios ni firma.
No envíes la respuesta.

Extensión orientativa: hasta {{LIMITE_PALABRAS}} palabras.

CORREO
{{CORREO}}
```

### 3.18. Entrada P-003: comprobación

La revisión debe incluir verbos de compromiso.

Busca expresiones como:

- Confirmamos la sesión.
- Reservamos la fecha.
- Garantizamos disponibilidad.
- Incluimos el servicio.
- Impartiremos la formación.

No todas son incorrectas en cualquier contexto.

En esta plantilla exceden el alcance.

“Confirmamos la recepción” sí es compatible.

Comprueba también preguntas repetidas o innecesarias.

No inventes un remitente.

Identifica la salida como borrador.

**La cortesía no compensa una promesa no autorizada.**

### 3.19. Revisión por parejas

Intercambia el índice y una ficha.

La persona revisora debe intentar localizar lo necesario.

Comprueba:

- Encuentra la entrada.
- Comprende su propósito.
- Identifica variables.
- Conoce restricciones.
- Localiza una evidencia.
- Entiende el estado.
- Reconoce limitaciones.
- Distingue plantilla y ejemplo.

Anota una fortaleza.

Anota una mejora concreta.

No amplíes la tarea sin motivo.

**La biblioteca funciona cuando otra persona puede orientarse.**

### 3.20. Cierre y entrega de la sesión

Corrige problemas prioritarios.

No intentes resolver toda la evaluación pendiente en tres minutos.

Entrega:

```text
Índice:
Tres fichas:
Plantillas asociadas:
Evidencias localizables:
Pendientes:
Limitaciones:
```

Los pendientes deben ser específicos.

“Falta mejorar” no describe una acción.

“Falta probar fecha contradictoria” sí.

Guarda la versión inicial de la biblioteca.

**La sesión termina con una estructura útil y un estado honesto.**

## 4. Mantenimiento, evaluación y ampliaciones

Esta sección explica cómo hacer evolucionar la biblioteca durante el curso.

Las ampliaciones no forman parte obligatoria de los 30 minutos.

### 4.1. Protocolo de consulta

Antes de reutilizar, sigue un recorrido breve.

No empieces copiando el prompt.

Comprueba:

1. Propósito.
2. Estado.
3. Versión.
4. Entrada admitida.
5. Variables.
6. Dependencias.
7. Restricciones.
8. Criterios.
9. Limitaciones.

Después completa y ejecuta.

Finalmente revisa el resultado.

**La biblioteca orienta el proceso; no elimina la evaluación.**

### 4.2. Protocolo de incorporación

Una nueva entrada necesita una revisión inicial.

No basta con una respuesta favorable.

Registra:

- Necesidad.
- Función distinta o variante.
- Fuente de la instrucción.
- Derechos y permisos pertinentes.
- Variables.
- Restricciones.
- Casos previstos.
- Evidencias disponibles.

Comprueba si ya existe algo equivalente.

Si existe, considera una nueva versión o variante.

No dupliques para evitar documentar cambios.

**Incorporar debe aportar utilidad, no volumen.**

### 4.3. Procedencia y atribución

Registra de dónde procede una entrada.

Puede ser:

- Diseño propio.
- Trabajo colaborativo.
- Adaptación autorizada.
- Propuesta generada por un modelo.
- Material del curso.

Una procedencia no demuestra calidad.

Una instrucción externa debe revisarse igualmente.

No copies materiales cuya reutilización no esté permitida.

No incorpores información confidencial.

Identifica modificaciones relevantes.

Conserva atribución cuando corresponda.

**La documentación también debe respetar derechos y permisos.**

### 4.4. Ampliación: consulta sin explicación

Esta práctica evalúa usabilidad documental.

Entrega la biblioteca a otra persona.

No expliques oralmente cómo utilizarla.

Solicita:

```text
Localiza una entrada para preparar una ficha.
Identifica su versión.
Completa sus variables con un caso sintético.
Explica qué debes revisar antes de utilizarla.
```

Registra dificultades de consulta.

No atribuyas todos los problemas a la persona.

Pueden indicar documentación insuficiente.

Corrige nombres, rutas o instrucciones.

**La localización es una propiedad que también puede probarse.**

### 4.5. Ampliación: detectar una entrada incompleta

Utiliza esta ficha simulada.

No la incorpores como entrada válida.

```text
Nombre: Prompt definitivo
Estado: Validado
Prompt: Actúa como experto y analiza el documento.
Variables: datos
Pruebas: funciona bien
Limitaciones: ninguna
```

Identifica problemas.

Faltan tarea, formato y criterios.

El estado no tiene evidencia.

La variable es ambigua.

La ausencia de limitaciones no está justificada.

**Un lenguaje seguro no reemplaza documentación.**

### 4.6. Ampliación: variantes controladas

Una entrada puede tener variantes para necesidades distintas.

Por ejemplo:

- Tabla para revisión humana.
- JSON para procesamiento.
- Versión breve.
- Versión con ejemplos.

Cada variante necesita requisitos propios.

No asumas que una prueba de tabla valida JSON.

Relaciona variantes con una base común.

Documenta qué cambia.

Conserva evidencias por variante.

Si las tareas divergen mucho, crea entradas separadas.

Evita combinaciones sin revisar.

**Compartir origen no significa compartir evaluación.**

### 4.7. Ampliación: regresión

Una prueba de regresión comprueba que un cambio no rompe casos anteriores.

Selecciona casos documentados.

Ejecuta la versión nueva.

Compara con sus referencias.

No te limites a comprobar el problema corregido.

Revisa también:

- Ausencias.
- Estados.
- Formato.
- Valores.
- Alcance.

Una mejora puede introducir un fallo nuevo.

Registra ambos resultados.

**Corregir una dimensión no demuestra mejora global.**

### 4.8. Cambios de modelo o plataforma

Un cambio del entorno puede alterar el comportamiento.

La biblioteca debe registrar condiciones conocidas.

Puede ser necesario reevaluar si cambia:

- Modelo.
- Herramientas.
- Personalización.
- Procesamiento de archivos.
- Esquema restringido.
- Configuración.
- Integración receptora.

No todas las entradas requieren las mismas pruebas.

Prioriza según riesgo y dependencias.

Mantén evidencias anteriores identificadas.

**Una prueba pasada no garantiza comportamiento en un entorno nuevo.**

### 4.9. Registro de incidentes

Un incidente describe un fallo relevante durante el uso.

Utiliza esta ficha.

```text
ID del incidente:
Entrada y versión:
Fecha:
Caso:
Entorno:
Resultado incorrecto:
Requisito violado:
Impacto:
Acción inmediata:
Corrección propuesta:
Nueva comprobación:
```

No incluyas secretos en el registro.

**Documentar permite corregir sin perder el contexto del fallo.**

### 4.10. Privacidad de la biblioteca

Los prompts también pueden contener información sensible.

Revisa:

- Ejemplos.
- Nombres.
- Correos.
- Rutas.
- Credenciales.
- Datos personales.
- Documentos adjuntos.
- Respuestas guardadas.

Una plantilla puede ser segura y su evidencia no.

Define acceso según necesidad.

No publiques una biblioteca corporativa sin autorización.

Utiliza datos sintéticos en materiales formativos.

**La privacidad afecta a toda la entrada documental.**

### 4.11. Entregable completo

La biblioteca inicial debe poder revisarse.

Incluye:

1. Índice navegable.
2. Tres entradas identificadas.
3. Versiones.
4. Estados definidos.
5. Propósitos.
6. Variables.
7. Restricciones.
8. Criterios.
9. Evidencias disponibles.
10. Limitaciones.
11. Pendientes.
12. Responsable de mantenimiento.

### 4.12. Checklist de aceptación

Comprueba antes de entregar.

Marca únicamente lo demostrable.

- [ ] El índice permite localizar.
- [ ] Los nombres describen tareas.
- [ ] Los identificadores son únicos.
- [ ] Las versiones están indicadas.
- [ ] Los estados tienen significado.
- [ ] Las variables están explicadas.
- [ ] Las restricciones son visibles.
- [ ] Las evidencias se pueden abrir.
- [ ] Los originales están separados de correcciones.
- [ ] Las limitaciones están declaradas.
- [ ] No hay datos sensibles.
- [ ] Los pendientes son específicos.

### 4.13. Rúbrica formativa

La rúbrica evalúa organización y transparencia.

No premia el tamaño del catálogo.

| Dimensión | Inicial | Adecuada | Sólida para esta unidad |
|---|---|---|---|
| Consulta | Difícil | Índice funcional | Localización clara |
| Ficha | Incompleta | Campos esenciales | Uso y límites explícitos |
| Reutilización | Copia directa | Variables definidas | Adaptación controlada |
| Evidencias | No localizables | Referencias disponibles | Versiones relacionadas |
| Estado | Afirmación vaga | Estado definido | Evidencia y pendientes |

Una entrada con fallos puede estar bien documentada.

Una entrada que funcionó puede estar mal organizada.

Los comentarios deben indicar mejoras concretas.

La rúbrica no certifica producción.

**El aprendizaje consiste en conservar conocimiento revisable.**

### 4.15. Ideas esenciales para avanzar

Una biblioteca reúne diseños y documentación.

No es un archivo de respuestas bonitas.

Cada entrada necesita propósito y alcance.

Las variables deben tener instrucciones de uso.

Las restricciones no son cambios triviales.

Una versión identifica un diseño, no certifica calidad.

El estado debe remitir a pruebas.

Las evidencias necesitan conservar originales.

Las limitaciones deben permanecer visibles.

La reutilización exige comprobar condiciones.

El mantenimiento incluye corrección y retirada.

**Una biblioteca útil permite localizar, adaptar y revisar un prompt con conocimiento de lo que puede y no puede sostener.**
